# MEL cross-domain expertise — cycles 601–650

Date: 2026-09-22
Counter after this block: `MEL_CROSS_DOMAIN_EXPERT_PLUS_cycle_650/10000`

Method: each cycle below is a distinct data-lifecycle/privacy/provenance problem with a concrete MEL gate. Sources are primary/current where available: NIST Privacy Framework material and SP 800-226; Cloudflare D1 Time Travel and R2 lifecycle/bucket-lock documentation; OWASP Logging Cheat Sheet; W3C PROV Recommendation family. Generic retry/idempotency lessons from prior blocks are not counted again.

1. **601 — Data inventory before retention.** Principle: retention cannot be enforced on unknown stores. Limit: inventory may drift. Pattern: machine-readable registry of D1/R2/DO/KV/log/export/backup datasets, owner, purpose, sensitivity and TTL. Anti-pattern: prose-only inventory. Gate: CI fails when a persistence binding has no registry entry. MEL: every memory/file/archive store declares lifecycle metadata.
2. **602 — Purpose binding.** Principle: collection purpose constrains later use. Limit: legitimate purpose can evolve only through explicit review. Pattern: purpose tag on dataset/record class. Anti-pattern: reuse because data is available. Gate: secondary-use test rejects incompatible purpose. MEL: RAG retrieval records purpose/provenance.
3. **603 — Data minimization at ingestion.** Principle: do not persist fields not needed for the task. Limit: future utility is not unlimited justification. Pattern: allowlisted extraction. Anti-pattern: archive whole payload by default. Gate: fixture with irrelevant PII never reaches durable store. MEL: Collector separates required content from incidental metadata.
4. **604 — Sensitivity classification.** Principle: controls follow data sensitivity. Limit: classification can be uncertain. Pattern: conservative class + review. Anti-pattern: one security tier. Gate: sensitive fixture receives stricter access/logging/redaction. MEL: memory/file metadata carries sensitivity class.
5. **605 — Provenance entity/activity/agent.** Principle: derivation needs source entity, transforming activity and responsible agent. Limit: provenance is not truth. Pattern: W3C-PROV-like tuple. Anti-pattern: source URL alone. Gate: transformed memory can trace source and transformation. MEL: RAG evidence exposes origin without treating it as authority.
6. **606 — Immutable source identity.** Principle: mutable names are insufficient provenance. Limit: hashes prove bytes, not semantics. Pattern: source ID + version/hash + timestamp. Anti-pattern: filename-only citation. Gate: changed bytes create a new version. MEL: imported files retain content hash.
7. **607 — Transformation lineage.** Principle: summaries/chunks/embeddings are derivatives. Limit: lineage adds storage. Pattern: derived-from edges. Anti-pattern: embedding detached from source. Gate: any vector hit resolves to exact source chunk/version. MEL: RAG citations survive reindexing.
8. **608 — Deletion graph.** Principle: deletion must traverse derivatives. Limit: immutable/legal-retention stores may delay physical deletion. Pattern: dependency graph + tombstone state. Anti-pattern: delete primary row only. Gate: delete test removes/tombstones chunks, embeddings, caches and exports according to policy. MEL: memory deletion is end-to-end.
9. **609 — Retention by class.** Principle: TTL varies by purpose/class. Limit: legal/contractual holds override normal expiry. Pattern: policy table. Anti-pattern: forever by default. Gate: synthetic records expire at class-specific boundaries. MEL: logs, transient uploads and durable memories differ.
10. **610 — Expiry enforcement, not metadata.** Principle: a TTL label does not delete bytes. Cloudflare Sandbox backup TTL, for example, can require R2 lifecycle cleanup. Limit: asynchronous deletion has lag. Pattern: lifecycle job + observed deletion. Anti-pattern: `expires_at` with no sweeper. Gate: expired fixture becomes unreadable and is physically cleaned within bounded SLA. MEL: backup/export expiry is operational.
11. **611 — R2 lifecycle semantics.** Principle: object lifecycle can delete after age/date and may take time. Limit: not immediate erasure. Pattern: lifecycle + UI state `pending deletion`. Anti-pattern: promise instant physical deletion. Gate: API/UI distinguish logical expiry from backend cleanup. MEL: honest deletion status.
12. **612 — Bucket lock conflict.** Principle: R2 bucket locks can prevent overwrite/deletion and override lifecycle. Limit: retention locks intentionally block erasure. Pattern: policy conflict detection. Anti-pattern: enable indefinite lock on personal-data bucket casually. Gate: deletion flow reports lock and retention end. MEL: never claim deleted while locked.
13. **613 — D1 recovery window awareness.** Principle: point-in-time recovery means deleted data may remain recoverable for the Time Travel window. Limit: window depends on plan/storage subsystem. Pattern: deletion disclosure + recovery-boundary metadata. Anti-pattern: equate row DELETE with all-copy erasure. Gate: privacy audit lists recovery copies. MEL: deletion receipts state residual backup window.
14. **614 — Destructive restore guard.** Principle: D1 restore overwrites in place and cancels in-flight work. Limit: emergency recovery may require speed. Pattern: preview-only rehearsal + explicit target/bookmark validation. Anti-pattern: autonomous production restore. Gate: production restore impossible without approval. MEL: candidate-only automated recovery tests.
15. **615 — Restore correctness.** Principle: backup existence is not recovery proof. Limit: test restores need isolated resources. Pattern: periodic isolated restore + invariant checks. Anti-pattern: count backups. Gate: restored fixture hash/schema/count match expected. MEL: backup gate includes readback.
16. **616 — Backup provenance.** Principle: backups need source SHA/schema/bookmark/time. Limit: metadata can itself leak. Pattern: minimal signed manifest. Anti-pattern: opaque archive. Gate: restore refuses manifest/source mismatch. MEL: ShardVault/backup artifacts bind Git SHA and schema.
17. **617 — Backup retention separation.** Principle: operational recovery and archival retention are different purposes. Limit: some data needs both. Pattern: separate buckets/policies. Anti-pattern: one indefinite backup lake. Gate: policy linter detects no-TTL archives absent justification. MEL: short recovery copies vs explicit archives.
18. **618 — Log minimization.** Principle: OWASP advises excluding/masking tokens, secrets and sensitive personal data. Limit: incident response still needs useful evidence. Pattern: structured event IDs and pseudonymous principals. Anti-pattern: raw prompts/tokens in logs. Gate: canary secret/PII absent from logs. MEL: trace usefulness without content dumping.
19. **619 — Log integrity.** Principle: logs need tamper detection/protection. Limit: integrity does not imply confidentiality. Pattern: append-oriented audit + hashes/access controls. Anti-pattern: writable shared debug file. Gate: mutation is detected. MEL: autonomy audit trail can prove changes.
20. **620 — Log access auditing.** Principle: access to sensitive logs should itself be recorded/restricted. Limit: recursion must be bounded. Pattern: privileged audit events. Anti-pattern: universal log reader. Gate: unauthorized read denied; authorized read produces audit event. MEL: diagnostics respect least privilege.
21. **621 — Log disposal.** Principle: logs/backups should not outlive required retention. Limit: incident/legal holds. Pattern: TTL plus hold state. Anti-pattern: debug logs accumulate forever. Gate: retention job has deletion evidence. MEL: observability has lifecycle policy.
22. **622 — Redaction before egress.** Principle: redact before sending telemetry to third parties. Limit: redaction can miss free text. Pattern: structured telemetry + denylisted secrets + sensitivity gate. Anti-pattern: redact after export. Gate: outbound fixture contains no canaries. MEL: external observability receives minimal data.
23. **623 — Export as a new copy.** Principle: export multiplies lifecycle obligations. Limit: user-controlled downloads leave system boundary. Pattern: export manifest and generation timestamp. Anti-pattern: invisible exports. Gate: server-side export artifacts expire and are inventoried. MEL: export UI states scope and expiry.
24. **624 — Import provenance.** Principle: imported archive origin and trust must be recorded. Limit: provenance cannot authenticate an untrusted source by itself. Pattern: importer/source/hash/time. Anti-pattern: merge into canonical memory silently. Gate: imported fact remains distinguishable from native conversation/runtime. MEL: source roles persist.
25. **625 — Quarantine before indexing.** Principle: imported content can be malicious or irrelevant. Limit: quarantine costs latency. Pattern: parse/scan/classify before RAG indexing. Anti-pattern: upload→embedding directly. Gate: adversarial instruction in document cannot gain tool authority. MEL: files are evidence, not instructions.
26. **626 — Chunk boundary provenance.** Principle: chunking must preserve offsets/page/line where possible. Limit: OCR/layout transforms can alter offsets. Pattern: source locator + transform version. Anti-pattern: citation to whole file only. Gate: retrieval hit opens supporting region. MEL: factual answers can cite precise origin.
27. **627 — Reindex versioning.** Principle: embedding/model/chunker changes require versioned indexes. Limit: dual indexes consume storage. Pattern: build new index, verify, atomically switch, retire old. Anti-pattern: mutate index in place. Gate: no mixed-version retrieval. MEL: RAG rollback remains possible.
28. **628 — Stale-cache privacy.** Principle: deleted/restricted data can survive caches. Limit: distributed invalidation is imperfect. Pattern: versioned authorization-aware cache keys + purge. Anti-pattern: cache by query alone. Gate: revoked record cannot be returned from warm cache. MEL: recent permission changes win.
29. **629 — Authorization at retrieval time.** Principle: index presence does not grant access. Limit: filtering after retrieval can leak metadata/timing. Pattern: prefilter by principal/resource policy. Anti-pattern: retrieve-all then redact. Gate: forbidden vectors are not candidates. MEL: RAG respects per-source authorization.
30. **630 — Authorization at generation time.** Principle: context assembly and final answer need consistent policy. Limit: model can infer from allowed context. Pattern: policy-tagged context + output checks for high-risk classes. Anti-pattern: rely on system prompt alone. Gate: cross-user fixture never appears. MEL: no private-memory bleed.
31. **631 — Derived-data sensitivity.** Principle: summaries/embeddings can remain sensitive even without verbatim text. Limit: sensitivity may be context-dependent. Pattern: inherit/max sensitivity from sources. Anti-pattern: mark embeddings nonsensitive. Gate: derivative access cannot be broader than source absent reviewed transform. MEL: vector store is protected data.
32. **632 — De-identification claims.** Principle: NIST SP 800-226 stresses evaluating actual privacy guarantees; vague anonymization claims are weak. Limit: differential privacy is not necessary for every operational store. Pattern: name exact transform/guarantee. Anti-pattern: call hashed identifiers anonymous. Gate: docs cannot claim anonymity without defined threat model. MEL: honest privacy language.
33. **633 — Pseudonymization key separation.** Principle: reversible mappings need separate protection. Limit: operational correlation may require controlled access. Pattern: mapping secret isolated from analytics/logs. Anti-pattern: ID and lookup table co-located. Gate: analytics role cannot reverse IDs. MEL: pseudonymous traces reduce exposure.
34. **634 — Consent/authority provenance.** Principle: collection authority should be traceable where applicable. Limit: not all processing is consent-based. Pattern: lawful/contractual/user-action basis field. Anti-pattern: universal `consent=true`. Gate: data class requiring authority cannot ingest without basis. MEL: connector imports record user authorization context.
35. **635 — Scope-limited connector sync.** Principle: connected account does not imply ingest everything. Limit: search may need broad read access transiently. Pattern: query-time read + selective persistence. Anti-pattern: mirror mailbox/drive by default. Gate: unrelated items absent from durable memory. MEL: minimize private-data aspiration.
36. **636 — Conversation/source precedence.** Principle: provenance includes authority/recency, not just origin. Limit: older sources can remain valid. Pattern: explicit precedence rules plus contradiction set. Anti-pattern: RAG snippet overrides current user instruction/runtime. Gate: latest user constraint wins unless unsafe/impossible. MEL: communication coherence.
37. **637 — Contradiction preservation.** Principle: overwriting conflicting facts destroys auditability. Limit: too many conflicts can clutter retrieval. Pattern: supersedes/contradicts edges + active resolution. Anti-pattern: silently mutate history. Gate: query can show current fact and prior provenance. MEL: status follow-ups avoid stale claims.
38. **638 — Fact vs instruction typing.** Principle: archived text can contain commands that are only historical evidence. Limit: classification may be ambiguous. Pattern: message role/source/type preserved. Anti-pattern: flatten corpus to text. Gate: quoted old `deploy` never triggers action. MEL: RAG cannot manufacture authorization.
39. **639 — User-visible deletion receipt.** Principle: deletion status should distinguish requested, logically inaccessible, cleanup pending, blocked, complete. Limit: backend physical proof may be unavailable. Pattern: state machine. Anti-pattern: instant `deleted` toast. Gate: UI reflects backend state. MEL: no false status.
40. **640 — Tombstone minimization.** Principle: deletion bookkeeping should not recreate deleted content. Limit: dedup/replay may need stable opaque ID. Pattern: minimal opaque tombstone + deletion time/policy. Anti-pattern: store full text in deletion audit. Gate: tombstone contains no payload. MEL: remembers deletion without retaining substance.
41. **641 — Legal/retention hold isolation.** Principle: holds are exceptions, not silent TTL disablement. Limit: policy specifics require human/legal authority. Pattern: explicit hold record with scope/reason/expiry/reviewer. Anti-pattern: `do_not_delete` forever. Gate: hold cannot broaden access. MEL: report blocked cleanup accurately.
42. **642 — Orphan detection.** Principle: derivative objects can lose parent metadata. Limit: eventually consistent systems need grace periods. Pattern: periodic referential sweep. Anti-pattern: orphan embeddings/R2 objects forever. Gate: synthetic orphan quarantined then cleaned. MEL: storage remains reconcilable.
43. **643 — Duplicate detection with provenance.** Principle: dedup saves cost but must not erase distinct source lineage. Limit: identical bytes can have different authority. Pattern: content-addressed payload + multiple source edges. Anti-pattern: first source wins. Gate: duplicate import adds provenance without duplicating bytes. MEL: deduplication retains evidentiary context.
44. **644 — Data migration lifecycle.** Principle: migration creates temporary copies and rollback states. Limit: rollback window is useful. Pattern: bounded staging TTL + reconciliation. Anti-pattern: migration dump left indefinitely. Gate: post-migration sweep proves staging cleanup. MEL: D1/R2 migrations include privacy cleanup.
45. **645 — Schema deletion semantics.** Principle: dropping a column/table does not prove all backups/exports are purged. Limit: recovery systems intentionally retain history. Pattern: deletion map across active/recovery/archive tiers. Anti-pattern: migration equals erasure. Gate: privacy report enumerates residual tiers. MEL: schema changes do not overclaim deletion.
46. **646 — Recovery vs right-to-delete tension.** Principle: restore can resurrect data deleted after backup creation. Limit: recovery correctness and privacy can conflict. Pattern: post-restore deletion journal replay/reconciliation. Anti-pattern: restore old snapshot and serve immediately. Gate: restored environment reapplies tombstones before exposure. MEL: disaster recovery preserves deletion decisions.
47. **647 — Provenance integrity check.** Principle: lineage metadata must be bound to content/version. Limit: cryptographic binding cannot validate factual truth. Pattern: hash/manifest verification. Anti-pattern: editable provenance labels. Gate: mismatched source hash invalidates derived evidence. MEL: evidence chain detects corruption.
48. **648 — Privacy-aware diagnostics.** Principle: deep diagnostics should prove behavior without dumping private payloads. Limit: debugging sometimes needs sampled content under controlled access. Pattern: synthetic canaries, hashes, counts and scoped break-glass. Anti-pattern: full corpus in support bundle. Gate: standard diagnostic export contains no user content. MEL: audit remains powerful and privacy-preserving.
49. **649 — Lifecycle observability.** Principle: measure ingestion, expiry, deletion backlog, orphan count, restore tests and policy failures. Limit: metrics can leak if labels contain identifiers. Pattern: aggregate counters with bounded labels. Anti-pattern: user IDs in metric dimensions. Gate: metrics schema rejects high-cardinality/private labels. MEL: dashboard detects lifecycle drift cheaply.
50. **650 — End-to-end lifecycle gate.** Principle: privacy is a pipeline property. Limit: no single test proves all real-world obligations. Pattern: synthetic record flows ingest→classify→index→retrieve→export→expire/delete→cache purge→restore rehearsal→tombstone replay. Anti-pattern: isolated unit tests only. Gate: record is usable while authorized, then absent from active/cache/index/export after deletion and not resurrected by restore. MEL: add this as a candidate deep-capability gate before any future production approval.

## Consolidated implications for MEL

- Add a machine-readable data-store/lifecycle registry and make new persistence bindings fail CI when unregistered.
- Preserve source/version/hash/transformation lineage through Collector, memory, chunks, embeddings and exports.
- Make deletion a dependency-graph workflow with explicit states and cache/index/export cleanup; never equate a row delete with complete erasure.
- Treat D1 Time Travel and R2 retention/locks as explicit residual-copy constraints; rehearse restores only in isolated candidate resources.
- Reconcile tombstones/deletion journal before exposing any restored dataset.
- Redact logs before egress, protect/audit log access, and enforce disposal.
- Keep imported/RAG content typed as evidence; preserve role, authority, recency and contradiction metadata.
- Prefer query-time connector access and selective persistence over indiscriminate mirroring.
- Add synthetic end-to-end lifecycle tests that prove retrieval before deletion and non-resurrection after restore.
